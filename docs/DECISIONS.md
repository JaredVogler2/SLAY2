# SLAY2 implementation decisions (living log)

This file is initialized during prompt-authoring only. Claude Code must add a dated ADR entry with context, chosen approach, alternatives, testing evidence, patch/build and rollback conditions whenever making a consequential implementation or model-policy decision. Existing initial architecture choices and their rationales are in [ARCHITECTURE-DECISIONS.md](ARCHITECTURE-DECISIONS.md).

## 2026-10-25 — Initial scope

Original new **Slay the Spire 2**, solo-first, 5-character / 3-act / Ascension A0–A10 versioned scope as of current research, independently researched from STS1; co-op separately validated; premium manual-first Vercel web frontend; offline simulation/training; source license and patch parity gated. The application, simulation and models are not implemented yet. Changes to mechanics or current features must be reverified against newest official release.

## 2026-10-25 — ADR-011: use rights-restricted third-party references locally, never vendored

**Context.** The owner's `/goal` directed SLAY2 to use `zhiyue/sts2-rl-agent` (unlicensed; 3,426 decompiled Mega Crit C# files for v0.107.1; Python simulator; RL scripts) and `nkhoit/spire-archive` (unlicensed; data extracted from PCK + decompiled C#). Earlier project rules forbade vendoring extracted game code. See [IP-COMPLIANCE.md](IP-COMPLIANCE.md) §3 for the full text.

**Decision.** Use both as **pinned (`external/pins.json`), local, read-only, git-ignored inputs**: (1) read the decompiled sources to *verify rules* and cite facts by file path (evidence class E1); (2) execute the simulator locally for research, labelling its output *simulator, live-game parity UNVERIFIED*; (3) read spire-archive data to cross-check ids/rarity/cost/type and patch history. Nothing from either repository is copied into SLAY2; `scripts/guard-third-party.sh` (pre-commit + CI) enforces this.

**Alternatives rejected.** (a) Vendoring the simulator/decompiled code - infringes Mega Crit's copyright and the authors' default rights, and would put it on a public repo. (b) Ignoring both - loses the only available source-level ground truth for v0.107.1 and the only full-run environment. (c) Waiting for upstream licenses - indefinite.

**Evidence.** Rules verified against E1 now match two independent secondary sources (sts.wiki, Almanauts) on every value checked, and resolved the A7 base-rate contradiction (1.49 %). Simulator reward generation passes a 28-check differential against our exact model.

**Rollback.** If a rights holder objects: delete E1 citations, re-support rules with E3/E4/live-game evidence, drop any derived catalog; the guard ensures no third-party files are in history.

## 2026-10-25 — ADR-012: run-outcome taxonomy and "never trust the gym wrapper"

**Context.** `STS2RunEnv.step()` swallows every exception and calls `lose_run()`, and records timeouts as losses. Our first smoke test produced 10/10 "deaths" that were actually `FileNotFoundError`s (cwd-relative data path).

**Decision.** Evidence-grade runs drive `RunManager` directly and classify every episode as exactly one of `win | death | timeout | simulator_error | invalid_action | aborted`. Only `win`+`death` are *completed games*; the others are reported separately and never silently dropped or counted as losses. The harness runs with cwd = the simulator checkout, starts runs with `start_with_neow=True`, and treats any exception as `simulator_error`.

**Consequence.** Win rate = wins / (wins + deaths), with the denominator and all other classes printed beside it; Wilson intervals on the binomial.

## 2026-10-25 — ADR-013: exact rational arithmetic for odds

**Decision.** `packages/odds` computes with BigInt rationals (no floating point) so that distributions sum to exactly 1, golden values are exact fractions, and brute-force enumeration can be compared with `===`. Floats appear only at the display boundary. Game floats are float32 thresholds; the difference (<= 1e-7) is documented and tested as a tolerance in the simulator audits, not in the engine.

## 2026-10-25 — ADR-014: rule sets are pinned per build and the engine refuses unverified builds

**Decision.** Every calculator takes a `RuleSet` (`sts2-main-0.107.1`). Requesting beta v0.111.0 (or any unknown build) returns `status: "unsupported_build"` with the reason; there is no silent fall-back. Known main/beta differences (White Beast Statue/potion counter; card rarities) are recorded in `docs/game/MECHANICS-COVERAGE.md` §10.

## 2026-10-25 — ADR-015: Python research harness lives in `sim/`, separate from the web app

**Decision.** Simulation, policies, audits and training are Python under `sim/` (original code), importing the simulator from the ignored checkout via `SLAY2_EXTERNAL_ROOT`. The Next.js app never imports or shells out to it (Vercel is not a compute platform for simulation). Exact-odds fixtures flow one way: TS engine -> JSON golden files -> Python audits.

## 2026-10-25 — ADR-016: explicit profile cohorts and mandatory event registration

**Context.** Measurement showed (a) every simulator run defaults to the profile's *first-ever run* (scripted early packs/potions/"?" rooms) and (b) the 68 events, including Neow and the Ancients, are not registered unless `sts2_env.events` is imported - which the gym env and training scripts never do.

**Decision.** `external.activate()` imports `sts2_env.events`. Every batch records a `profile` in its config: `veteran` (default; `number_of_runs=10`, `epoch_unlock_count=20`) or `first_run`. Cohorts are never pooled in a headline metric. The profile is applied by temporarily swapping `RunManager`'s `RunState` for a subclass so the unlock state is set before the opening Ancient event (constructor flow otherwise unchanged).

**Consequence.** Batches produced before this change (which lacked events) were discarded and regenerated; none are cited.

## 2026-10-25 — ADR-017: closure-aware cloning is the only permitted forward model

**Context.** Plain `copy.deepcopy` of a run diverges from the live run at the enemy turn (38/80 sequences) because function closures are copied by reference.

**Decision.** Search and any lookahead use `slay2_sim.clone.clone_manager` (closure cells rebound through the deepcopy memo) followed by `fair_determinize` (canonical-sort-then-shuffle of the draw pile and reseeding of every reachable RNG). Both properties are tested: clone fidelity (0 divergences) and counterfactual invariance (equal observations/determinized state for different hidden states).

**Alternatives rejected.** Replay-from-scratch per node (O(history) per node); hand-written enemy-turn models (re-implements the simulator and its bugs).

## 2026-10-25 — ADR-018: toolchain pins (exact versions, verified against the npm registry on 2026-10-25)

**Decision.** Node 22 (`.node-version`, `engines >=22.12`), pnpm 10.28.0 (`packageManager`), Next.js **16.4.3** (App Router, Turbopack), React 19.3.1, **TypeScript 6.0.3**, ESLint 10.13.0 (flat config) with typescript-eslint 8.72.0 and eslint-config-next 16.4.3, Vitest 5.0.5, fast-check 4.10.2, Zod 4.6.7, Tailwind 4.3.3, Prettier 3.9.10, Playwright 1.64.1 + axe-core/playwright 4.14.0. Every version is pinned exactly; `pnpm-lock.yaml` is committed and CI installs with `--frozen-lockfile`.

**Why not the newest.** TypeScript 7.0.2 is published, but typescript-eslint 8.72.0 declares `typescript >=4.8.4 <6.1.0`, so type-aware linting would be unsupported; revisit when typescript-eslint supports 7. `jsdom` is pinned to 29.1.1 because 30.x requires Node >=22.22.2 and the build container has 22.22.0. `@types/node` is pinned to the 22 line to match the runtime.

**Known wrinkles (checked, not hidden).** (1) TypeScript 6 defaults `types` to `[]`; each package opts in (`"types": ["node"]`). (2) `eslint-config-next` pulls three plugins whose declared peer range stops at ESLint 9; ESLint 10.13 runs them cleanly on this code base (`pnpm lint` green) - if a rule crashes in future, downgrade ESLint to 9.x rather than disabling lint. (3) Licenses (2026-10-25, `pnpm licenses list`): 357 MIT, 26 Apache-2.0, 14 ISC, 9 BSD-2, 3 BSD-3 and a few others; non-permissive entries are MPL-2.0 (axe-core, lightningcss: dev/build only), CC-BY-4.0 (`caniuse-lite` data, build only), **LGPL-3.0-or-later** (`@img/sharp-libvips-*`, optional prebuilt binaries pulled in by Next's `sharp`; SLAY2 does not use `next/image` optimisation, the libraries are dynamically linked and unmodified), OFL-1.1 (Fontsource fonts: Inter, Cinzel, JetBrains Mono). `pnpm audit`: no known vulnerabilities.

**Fonts.** Fontsource (OFL-1.1) packages are bundled into the build; no request to Google Fonts is made by visitors.


## 2026-10-26 — ADR-019: facts-only card catalog (`packages/game-data`)

**Context.** The advisor, reward pools and card picker need card identity, class, rarity, cost and type. The only complete source for v0.107.1 is the pinned local decompilation (E1) cross-checked against spire-archive's extracted data, both rights-restricted (ADR-011).

**Decision.** The catalog is derived by `python -m slay2_sim catalog`; for each card it keeps **only** the canonical id, display name, class, rarity, energy cost, card type, whether it is reward-eligible, and SLAY2's own role tags written by us. **No card text, flavour text or descriptions.** The output (577 cards, sha256 `6717e3d5d311…`) is committed with provenance flags; `docs/game/CATALOG-CROSSCHECK.md` records the cross-check, including the disagreements. Solo reward pools are 20/35/25 cards per class by rarity (Q3 closed); epoch-gated cards reduce the pool for new profiles and the API says so.

**Alternatives rejected.** Mirroring a third-party card database (rights, ADR-011); hand-typing cards (error-prone); fetching a public API at request time (availability, terms, and the site must work offline).

**Rollback.** Delete the catalog and fall back to ids typed by the user; the odds engines do not depend on it (they take counts).

## 2026-10-26 — ADR-020: the card advisor is a labelled heuristic (v0), never a probability

**Context.** No fair-information policy has won a simulated game yet (0 wins in 2,499 completed veteran-profile games), so there is no outcome evidence to calibrate card values against.

**Decision.** `evaluateDraft()` ranks the offered cards and skip by the change in a **unit-less deck-quality index** (average card quality with dilution, act-dependent role coverage with diminishing returns, energy curve, deck size, strength × multi-hit synergy). The output contains legal actions only, a reason list per option, the **stability** of the top choice under ±40 % jitter of its own weights, warnings, assumptions and an explicit not-modelled list. It refuses the beta build, unknown ids and duplicates. The UI and API call it "heuristic v0, not calibrated"; `/methods` lists "advisor win delta" under *not yet evaluated*. The catalog prior is rarity-banded with a capped adjustment (an unbounded version scored one rare 95).

**Alternatives rejected.** Presenting a win-probability delta (no evidence); copying a tier list (rights and staleness); an LLM judgement (not reproducible, not testable).

**Evidence.** 13 decision tests (contract, legality, determinism, behaviour, validation, 120 random requests); e2e shows a curse is never recommended over skipping.

**Rollback / upgrade path.** Replace the index with a simulator-calibrated value (card-probing harness, phase 05) only after a paired comparison on held-out seeds shows an effect; keep v0 as the champion until then.

## 2026-10-26 — ADR-021: web state is local-first

**Decision.** The player's run lives in `localStorage` (key `slay2.run.v1`) as `RunState` v1, validated by a strict zod schema on every load and import; imports are capped at 256 KB; undo/redo is session-only (50 steps); export is plain JSON. There are no accounts, cookies, analytics or server persistence, and the pages issue no client `fetch` (checked by search). The HTTP API is stateless and exists for tools, tests and a future companion. Blocked storage degrades to in-memory state with a visible notice.

**Alternatives rejected.** Server-side accounts and a database (privacy, abuse, and legal surface for a fan site); IndexedDB (no need at this size); sync across devices (a later, opt-in feature that would need its own threat model).

**Consequence.** Support requests cannot be debugged from server data; `/about` says so, and export/import is the supported way to move a run.

## 2026-10-26 — ADR-022: nothing measured is typed by hand on the website

**Context.** A review found that `/methods` stated "about 18× slower" and "16.0 vs 18.3 mean floor on the same seeds" in prose. The data say **19.7×**, and the 18.3 was the mean over 300 games while the search batch covered the first 200 of the same seeds (**18.41 vs 16.04** on the 200 shared seeds).

**Decision.** (1) Rules, batches, comparisons and gaps reach the site only through `scripts/export-site-data.mjs`, and a test fails when the generated JSON is stale. (2) A paired comparison is a first-class committed artifact (`experiments/comparisons/*.json`, written by `slay2_sim compare --out`) with the content hashes of both batches; the exporter **throws** if either batch changed afterwards (tested by tampering with a copy). (3) Sentences about results are generated from those artifacts (`comparisonSentence`), including the verdict rule: a side is "higher" only if the whole 95 % bootstrap interval excludes zero. (4) Headline claims such as "no policy has won" are computed (`totals()`), so they flip automatically when a win appears.

**Alternatives rejected.** Reviewing prose by eye (this is how the error got in); a CMS (no editorial need).

## 2026-10-26 — ADR-023: interim Content Security Policy

**Context.** Pages are statically generated. Next.js applies nonces only during dynamic rendering, so a nonce-based `script-src` would turn every page into a per-request render and give up the CDN cache. The inlined hydration payload needs either a nonce or `'unsafe-inline'`.

**Decision.** Ship now: `default-src 'self'`, `script-src 'self' 'unsafe-inline'` (plus `'unsafe-eval'` and websockets in `next dev` only), `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: blob:`, `font-src 'self'` (fonts are bundled), `connect-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`; plus `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, a restrictive `Permissions-Policy` and `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains`/`preload`; that is the domain owner's commitment). The interim policy is acceptable **because** the site renders no user-supplied HTML: there is no `innerHTML` sink, imports pass a strict schema, and an e2e test loads every page under the policy and fails on any violation.

**Tighten when:** any feature renders untrusted markup, a companion/bridge page is added, or monetization is considered. Then move HTML routes to dynamic rendering with a proxy-issued nonce (`strict-dynamic`) and drop `'unsafe-inline'` for scripts.

## 2026-10-26 — ADR-024: known simulator gaps are data that travel with every result

**Context.** The third-party simulator never enters the A10 Double Boss, scales three monsters' HP incorrectly at A8, crashes on `is_sovereign_blade(None)`, uses an older RNG family, and has no live-game parity. A win rate that omits these would be read as a statement about the real game.

**Decision.** `sim/slay2_sim/gaps.json` is the single source of truth (read by the harness and by the website exporter). Every batch manifest records the gaps that apply to its configuration (ascension thresholds); `/methods` prints them beside the results; the A10 Double Boss gap has a **strict xfail** test, so fixing the simulator (or our harness) turns the test red until the gap record is removed deliberately.

**Consequence.** Results from ascension 10 from this simulator cannot be described as Double Boss results.

## 2026-10-26 — ADR-025: patch diffs record ids and field names, never content

**Context.** Early Access patches change numbers weekly, and the only versioned data we may touch is rights-restricted (ADR-011). We still need to know *what to re-verify* after a patch.

**Decision.** `python -m slay2_sim patchdiff <old> <new>` compares the pinned spire-archive snapshots (0.99.1, 0.103.2, 0.107.1) and writes ids added/removed, categorical facts that changed (class, rarity, cost, type, target, tier) with old/new values, and only the **names** of other fields that changed (`text`, `vars`, `upgrade`, ...). Names, descriptions and numbers are never copied. A field the archive populated later is reported as `extraction_only`; a field present in one snapshot only is a schema difference; neither counts as a game change. `--coverage` lists v0.107.1 ids missing from the pinned simulator (after normalising the `_CARD`/`_STATUS` suffix the simulator adds).

**Evidence.** 0.103.2 -> 0.107.1: cards +2/-1 with five categorical changes that the committed catalog already carries; relics +3; potions unchanged. Simulator id coverage of v0.107.1: 577/577 cards, 296/296 relics (id coverage only; parity stays UNVERIFIED). Tests cover the semantics with synthetic snapshots, prove no content leaks, and check invariants of the committed diffs.

**Alternatives rejected.** Committing before/after values (content); trusting the archive's own change log text (content and unverifiable); diffing the simulator instead (it would hide the simulator's own errors).

**Rollback.** Delete `docs/patches/`; nothing else depends on the files at run time.

## 2026-10-26 — ADR-026: combat policy is learned from real run states with a fair encoding, and judged by paired evaluation

**Context.** Diagnostics over 160 simulated runs show the rules policy loses ~58 of ~74 HP to the Act 1 boss and dies there 48% of the time, and dies in 20% of Act 2 ordinary fights. Combat quality is the first limit on any simulated win and on any simulation-based card evidence. Search over the simulator is too slow (a clone costs ~2.5 ms), so a learned policy is the practical lever.

**Decision.**
1. *Environment* (`sim/slay2_sim/rl/env.py`): a single-combat environment whose start states are snapshots of real runs taken **before the entering action**; `reset` clones one, re-randomises every hidden stream, and enters the fight. Decks, relics, potions and HP are therefore realistic, and each reset has a new opening hand. Reward per decision is `-0.5 * HP lost / max HP`, `-0.1` per potion, `+1` win, `-1` death or step cap.
2. *Fairness*: the network input is `features.encode(observation)`, a pure function of the allow-listed observation (draw pile as a multiset, no RNG, no future). A test perturbs the draw order and every RNG stream and requires bit-identical encodings.
3. *Model*: a small transformer over entity tokens (player, hand cards, enemies, piles, relics, potions, pending choices) with slot-pointer action heads, so one set of weights serves every hand position and target. Illegal actions are masked.
4. *Training*: synchronous PPO (GAE 0.95, clip 0.2) with local-inference worker processes; training libraries come from the `train` seed partition only.
5. *Judging*: paired greedy evaluation of `rules` and the network on identical (held-out `val` snapshot, hidden-stream seed) pairs, McNemar for wins and a paired bootstrap for HP lost; then run-level paired batches (`ppo_combat_v1` vs `rules_v1`) on `val`; the sealed `test` partition is read once, for the final candidate.
6. *Artifacts*: checkpoints are never committed (weights derived from a third-party simulator are audited separately); a finished run is summarised by config, metrics and the checkpoint SHA-256.

**Alternatives rejected.** Training from scratch on the starter deck only (not the distribution the policy will meet); a flat MLP over concatenated slots (no weight sharing across slots, slow to learn); end-to-end full-run RL first (sparse reward, the combat part dominates the variance); the simulator's own gym wrapper (turns exceptions and timeouts into losses, ADR-012).

**What would count as success.** A paired improvement on held-out combats with the confidence interval excluding zero **and** a run-level improvement in mean floor on `val`. Anything less is reported as a negative result.

**Outcome of run 1 (2026-10-26, negative).** Training from random weights was stopped at iteration 189 of 300 (2.9M steps) because the greedy validation win rate had stayed between 83.5 % and 85.7 % since iteration 60, below the baseline. Paired evaluation on the same 796 held-out `val` pairs (`experiments/rl/results/combat-ppo-v1-run1.json` and the per-pair artifact beside it): `rules` 86.6 % (95 % Wilson 84.0-88.7), network `best.pt` (iteration 90, selected on validation, so optimistic) 85.7 %, McNemar p = 0.43, `latest.pt` (iteration 180) 84.1 %, p = 0.019 in favour of `rules`; HP lost differs by less than one percentage point with intervals spanning zero. The network uses about a third of the potions (0.20 vs 0.62 per combat; bosses 0.88 vs 1.79). **The success bar was not met**, no run-level batch was run, nothing is deployed. Next: behaviour-cloning warm start from `rules_v1` on the `train` partition (`rl/bc.py`), then PPO at a lower learning rate, evaluated the same way; the potion cost in the reward is a suspect to test, not a finding.

## 2026-10-26 — ADR-027: the odds API does not guess what the caller did not state

**Context.** The first red-team round (docs/ADVERSARIAL-AUDIT.md, RT-3-01 and RT-2-04) found two places where an omission silently became a confident number. A card-reward request with neither `counter` nor `history` was answered as if no reward had ever been offered (the start-of-run state); potion and "?" `history` were optional with the same default. `removal` and `gold` had no `build` field, so the unverified beta could not even be named, let alone refused, and the answer did not say which patch it was for.

**Decision.**
1. Calculators that depend on hidden state require the caller to say what they know: `counter`, or `history` where `[]` means "nothing has happened yet". Omission is a `400` that explains the choice. The potion and "?" `history` are required.
2. Every calculator that depends on the patch requires `build` and refuses an unverified one; `removal` and `gold` joined the others, and every answer echoes `build`.
3. Every answer states its `evidence` (`kind`: `history` or `counter`, and the number of observations), so a client can show how much a number rests on.

**Alternatives rejected.** Defaulting to the start of the run with a warning field (a client that ignores warnings shows a confident wrong number); defaulting `build` to the supported main build (hides that the caller is thinking of another patch).

**Evidence.** `apps/web/test/redteam.test.ts` RT-3-01..04 and RT-2-04 failed on the previous code and pass now; `apps/web/test/api.test.ts` was updated to the stricter contract.

**Rollback.** Revert the schema changes in `apps/web/src/lib/odds-api.ts`. Saved runs are unaffected (a run file stores its history, `[]` included).

## 2026-10-26 — ADR-028: exact arithmetic stays, untrusted input gets integer fast paths and caps taken from the game

**Context.** RT-10-07 and RT-10-13. Reward-rarity inference at Ascension 7 with a 100-pack unknown history took 179 s on the development machine because every posterior update normalised a `Rational`; a "?" history of 60 entries took about 17 s. Both histories come from strangers (API body or imported run file), so one request could occupy a serverless function for minutes.

**Decision.** `Rational` stays the specification and the public result type. The three inference hot paths are evaluated over integers instead: reward-pack tables are compiled once into integer weights over a common denominator (scale 10,000; the compiler asserts the weights are integral), posterior, forecast and position marginals are plain `bigint` sums normalised once at the end; "?" masses are integer percents (every probability there is a whole number of percent). Untrusted sizes are bounded by facts of the game: an act has fewer than 20 "?" rooms (`MAX_UNKNOWN_ROOMS_PER_ACT`, enforced in the engine, the API schema, the run-file schema and the UI), 100 pack observations, 200 potion observations.

**Evidence.** The previous rational implementations live on inside `packages/odds/test/fastpath.test.ts` as reference oracles and must agree with the fast paths on random inputs; the same file holds CPU budgets (a 20-entry "?" history in under 3 s, the A7 worst case in under 5 s, on a loaded machine). Measured on the development machine: A7 with 100 unknown packs 179 s to 0.44 s. `redteam.test.ts` RT-10-07 sends the worst legal request of every calculator through the route handlers and demands an answer in under 1.5 s each.

**Alternatives rejected.** Floating point (gives up the exactness the product is built on); memoisation only (the first request is the attack); a longer function timeout (pays for the attack instead of removing it); rate limiting alone (the expensive request is a single request).

**Rollback.** The reference implementations are still in the tests; swapping back is a one-file change that reopens RT-10-07.

## 2026-10-26 — ADR-029: the repository carries its own Vercel contract

**Context.** The owner imported the repository into a Vercel project with default settings (Root Directory `./`, no framework preset, Node 24.x). The first production build published nothing (it ran while `main` held documents only) and the second failed at install with `ERR_PNPM_UNSUPPORTED_ENGINE`: `apps/web` required Node 22.x, the project ran 24.x, and `.npmrc` sets `engine-strict=true`. Both left the production URL on a 404.

**Decision.** Make the default import work without dashboard settings, and keep the textbook layout working too (docs/DEPLOY.md): `engines.node` is the bounded `^22.12.0` in the root and in `apps/web` (Vercel maps it to the latest Node 22 and lets it override the project setting); `vercel.json` at the root sets framework `nextjs`, a frozen-lockfile install, the root `build` script and output `apps/web/.next`; `next` is also a root devDependency at the app's exact version because the Next.js builder resolves `next/package.json` from the project directory; `apps/web/vercel.json` selects the framework for the Root Directory `apps/web` layout. `apps/web/test/deploy-config.test.ts` pins all of it.

**Alternatives rejected.** Dashboard-only settings (not reproducible, and exactly what failed); the legacy `builds` key (disables project settings); `public-hoist-pattern[]=next` in `.npmrc` (an invisible pnpm detail instead of an explicit dependency); an open `>=` engines range (jumps major versions on its own and was the other half of the failure); supporting Node 24 now (not tested in CI, so not claimed).

**Evidence.** A clean checkout of the commit: `pnpm install --frozen-lockfile` and `pnpm run build` exit 0 and write the manifests the builder reads. A real Vercel preview build of the same commit: log lines "Node.js Version defined in your Project Settings ("24.x") will not apply, Node.js Version "22.x" will be used instead", "Detected Next.js version: 16.4.3", all 13 routes built, "Build Completed [33s]", deployment READY; `/`, `/api/v1/health`, `/api/v1/capabilities` and `/robots.txt` answered 200 with the security headers (through the platform's share link, protection stays on). Production verification is recorded in docs/DEPLOY.md only after the merge.

**Rollback.** Delete `vercel.json`, `apps/web/vercel.json` and the root `next` devDependency; the Root Directory `apps/web` layout keeps working.

## 2026-10-26 — ADR-030: dependency licences are a CI gate, not a review habit

**Context.** prompts/11 campaign 11: no dependency or artifact may put restricted terms inside a permissively licensed app.

**Decision.** `scripts/check-licenses.mjs` (CI step `pnpm licenses:check` after `pnpm guard`) lists licences with `pnpm licenses list --json` for the production tree and for everything. A production dependency must be MIT, Apache-2.0, ISC, BSD-2/3-Clause, 0BSD, OFL-1.1, Unlicense or CC0-1.0, or an explicit exception that names its packages and says why it is acceptable (LGPL-3.0-or-later `@img/sharp-libvips-*`: optional prebuilt libvips of Next's image optimiser, which SLAY2 does not use, dynamically linked and unmodified; CC-BY-4.0 `caniuse-lite`: build-time data; MPL-2.0 `axe-core` and `lightningcss`: unmodified file-level copyleft, test and CSS-build tools). Strong copyleft or non-commercial terms (AGPL, GPL, SSPL, BUSL, PolyForm, CC-BY-NC, Commons Clause) are refused anywhere in the tree, build tools included. An exception that no longer matches a package is reported so the list stays honest.

**Evidence.** On the current tree: production licences MIT 47, Apache-2.0 9, ISC 5, OFL-1.1 3, LGPL-3.0-or-later 2 (the exception), BSD-3-Clause 1, CC-BY-4.0 1 (the exception), 0BSD 1; "license gate: clean". `apps/web/test/licenses.test.ts` feeds synthetic trees through the script.

**Alternatives rejected.** A one-off audit (the next `pnpm add` would void it); denying all non-MIT (would drop Next's own optional image libraries and the accessibility test engine for no gain).

**Rollback.** Remove the CI step; the script is inert on its own.

## 2026-10-26 — ADR-031: card values are measured from randomised drafting, and only playing with them counts as validation

**Context.** The draft advisor ranks cards with a hand-written, unit-less index (`/advisor`, ADR-020): it has never been compared with an outcome. The simulator (unverified against the live game, gap G5) can play thousands of complete runs, so the question "does a card help?" can at least be asked about *simulated* play, and a policy that acts on the answer can be tested against the policy that does not.

**Decision.**

1. *Measure* (`slay2_sim/cardvalue.py`, tested on synthetic data with a known truth). `rules_explore` is `rules_v1` except that, with probability 0.6 per card reward, it picks uniformly among the offered cards and "skip" (its own RNG stream, replicate-numbered). Because chance, not taste, decided most of the drafted cards, a regression of "the run gets past the Act-1 boss" (logit) on the deck's card counts, the boss, the HP fraction, max HP, potions held, upgraded cards and the relics read off the deck at the boss fight gives each card a *marginal* coefficient `beta` (log-odds per extra copy, dilution included). Ridge penalty by 5-fold cross-validation grouped by game seed; intervals from a bootstrap over whole game seeds (200 draws). Data and result are committed: `experiments/cardvalue/explore-ironclad-a0-train-rep0/` (5,000 `train` games: 4,995 completed, 1 win, 3,812 reached the Act-1 boss) and `experiments/cardvalue/ironclad-a0-v1.json` (sha256 `8b3fe2f4d88b87dc…`); the result is reproduced byte for byte from the committed dataset with the command in the module docstring.
2. *Validate by intervention.* `rules_v2` is `rules_v1` with one change: on a card reward it takes the offered card with the largest `beta` if that `beta` exceeds `threshold` (0 = "one more copy helps on average") and the deck has fewer than 32 cards, otherwise it skips. The values file path and sha256 are policy parameters, so every batch manifest names the measurement it used.
3. *Pre-registered test (written before any `val` game of `rules_v2` exists).* Primary: `rules_v2` (`threshold=0`, values sha256 above) against `rules_v1` on the same 2,000 `val` seeds (disjoint from every game the values were fitted on, which used `train` seeds only), paired by seed. Primary endpoint: "got past the Act-1 boss", exact McNemar on the shared seeds, two-sided, α = 0.05. Secondary: floors reached (paired bootstrap), wins (expected to be zero on both sides). One run; no tuning of the threshold, the deck cap or the values on `val`; thresholds 0.1 and 0.25 may be run on the same seeds as a labelled sensitivity analysis and never used to pick the headline. The sealed `test` partition is not touched.
4. *Reading rule.* If the primary test shows an improvement, the values are published as "measured, and acting on them helped this pilot in simulation". If it shows no difference or a decline, they are published as associations only and the result is stated plainly next to them; the advisor is not recalibrated in either case until a better pilot or a live-game check exists.

**What a card value is not.** Not a statement about the real game (simulator unverified), not about other pilots (a card that `rules_v1` plays badly is undervalued; one it plays well is overvalued), not about synergies (the model is additive), not a tier list (conditioning on the other cards and on HP/relics is part of the definition). Shop purchases, events, rests and the first-reward pool are the pilot's own choices, not randomised, which confounds the cards that come from them.

**Alternatives rejected.** Reading values off winning runs only (there is one win in 5,000; "wins" cannot be the outcome yet); regressing on final floor (dominated by luck in later acts); a tabular win-rate per card (confounded by how often a good player takes it, which is exactly what randomisation removes); tuning the threshold on `val` (turns the held-out set into a development set).

**Rollback.** Delete `rules2.py` and `experiments/cardvalue/`; nothing else depends on them until the site shows the values.

**Outcome (the pre-registered test, run once on `val`; recorded 2026-10-26).** Batch `rules_v2-ironclad-a0-veteran-val-n2000`: 2,000 games, 1,994 completed (6 simulator errors, gaps G6/G7, excluded and never counted as losses), 6 wins and 1,988 deaths. Paired comparison `experiments/comparisons/rules_v2-vs-rules_v1-ironclad-a0-veteran-val.json` on the 1,991 seeds where both sides completed:

* *Primary endpoint, got past the Act-1 boss:* **65.1 % (1,296 games) against 43.3 % (863)**; 608 games only `rules_v2`, 175 only `rules_v1`, exact McNemar **p = 8.8e-57**. The pre-registered criterion is met by a wide margin (+21.8 percentage points).
* *Floors reached:* 21.05 against 18.08, **+2.96** (95 % bootstrap +2.61 to +3.32).
* *Wins:* **6 against 0** (6 games only `rules_v2`, none only `rules_v1`; exact McNemar p = 0.031; win rate 0.30 %, Wilson 0.14–0.66 %). These are the first wins on held-out seeds (the only earlier win was one exploration game on `train`, 1 in 5,000); each of the six was re-derived by `slay2_sim audit wins` (ADR-032): the stored record is reproduced by a fresh run, the trace replays observation hash for observation hash, the run is over and won, ended in the third act and entered exactly one boss fight per act.
* *Where it still dies:* deaths by act 695 / 1,185 / 114 (`rules_v1`: 1,132 / 837 / 28). The three Act-1 bosses still account for 484 deaths (834 for `rules_v1`); the next barrier is Act 2.

So acting on the measured values helped this pilot in simulation, by a lot; the reading rule's first branch applies. What it does **not** show: that the real game agrees (gap G5), that a better pilot would rank the cards the same way, or that any single coefficient is causal (the intervention changes all card choices at once). The advisor on `/advisor` is not recalibrated by this result; the measured values are shown next to the heuristic on `/codex` with their intervals (the advisor integration needs its own decision).

*Provenance note.* This batch was started before `run_batch` recorded the resolved policy parameters (ADR-032), so its manifest holds only `{"threshold": 0.0}`. The values file is identified by the hash fixed in this ADR before the run (the file is unchanged since commit `155afb6`), and `wins-audit.json` records the parameters the audit's re-runs resolved to (values sha256 `8b3fe2f4d88b87dc…`); that the re-runs reproduce the stored records is itself evidence that the same values were used. Later batches carry `policy.effective` in the manifest.

**Addendum: a neural alternative was tried and does not help (negative result).** `slay2_sim.cardvalue_nn` fits a ReLU network (three sizes, AdamW, dropout, early stopping on an inner group-wise split, three initialisations averaged) to the same 3,812 boss fights and 121 features with the same grouped folds. Held-out log loss: additive ridge-logistic **0.4386** (AUC 0.871); networks 0.4468, 0.4483, 0.4491 (AUC 0.865-0.866). Interactions between cards are not recoverable at this sample size, so the additive values stay (`experiments/cardvalue/mlp-vs-ridge-ironclad-a0-v1.json`). A larger sample (more replicates, other pilots) is the condition under which this should be tried again.

## 2026-10-26 — ADR-032: a win is re-derived before it is published; development seeds exist; manifests record the resolved policy

**Context.** The first wins of a full-run policy appeared (one exploration game, then six `rules_v2` games on `val`). A win is the strongest claim the harness makes and the one a simulator bug would fake most easily. Separately, `train` had been used to fit card values, so tuning on it is optimistic, and `val`/`test` must stay clean; and a manifest that records only the flags a batch started with cannot say which values file or checkpoint it used.

**Decision.**

1. `slay2_sim audit wins --batch <dir>` re-derives every win of a batch: it re-runs the seed with the policy the manifest names (the resolved parameters when recorded) and a trace, requires the fresh record to equal the stored one (outcome, floor, act, HP, deck, relics, combats, steps), replays the trace on a new run comparing every observation hash and legal-action count, and reads the replayed terminal state (run over, player won, final act index 2, exactly one boss fight per act; STS2 has no fourth act, no Heart). The result is `wins-audit.json` next to the batch and the traces (7–10 KB each) are committed under `wins/` (the batch's own `traces/` directory stays git-ignored). `scripts/export-site-data.mjs` **refuses to publish a batch with wins unless that audit passed for all of them**, so the website cannot show an unaudited win (`apps/web/test/methods-data.test.ts` tampers a copy to prove it).
2. The seed manifest `experiments/seeds/ironclad-a0-v2.json` keeps v1's `train`, `val` and `test` seeds exactly (a partition appended to the stream never moves an earlier one; regeneration of v1 is byte-identical and tested) and adds a 10,000-seed **`dev`** partition for development: policy tuning and the next round of card-value fitting use `dev`, never `train` (already used for the fit) and never `val`/`test` (held-out; `test` stays sealed). Batches on `train` and `dev` are labelled development results everywhere.
3. `run_batch` writes `policy.effective` (the version and the parameters the policy resolved to, e.g. a values file's path and sha256) into the manifest; `rules_v2` rebuilds from its own effective parameters and refuses a values file whose hash differs from the recorded one.

**Evidence.** `sim/tests/test_win_audit.py` (a 100,000-HP player reaches the win path; the audit verifies it, rejects a stored record the re-run does not reproduce, and claims nothing for a batch without wins); `test_stats_manifest.py::test_v2_manifest_keeps_every_v1_seed...`; `test_rules_v2.py` (effective parameters, hash refusal). All six `val` wins and the exploration win verified (`experiments/batches/rules_v2-ironclad-a0-veteran-val-n2000/wins-audit.json`, `experiments/cardvalue/explore-ironclad-a0-train-rep0/wins-audit.json`).

**Alternatives rejected.** Trusting `outcome == "win"` (the terminal flag is exactly what a simulator defect would set); auditing a sample (the cost is seconds per win); extending `train` in place (it would overlap `val`); recording only the CLI flags (what produced the 404-class confusion about which file a batch used).

**Rollback.** The audit is additive; removing the exporter gate restores the old behaviour. The v1 seed manifest is untouched.

## 2026-10-26 — ADR-033: the turn planner is judged by paired fights, and a value function that can be gamed is a bug

**Context.** `search_v1` (60 nodes, depth first, a static card order, a nested enemy-turn rollout per leaf) played fewer floors than the rules it was supposed to improve (+2.38 floors for `rules_v1`, 44.5 % vs 28.0 % past the Act-1 boss, 19.7x slower). `search_v2` replaced it with a best-first planner over distinct board states (play orders that reach the same board merge), a leaf valued as "end the turn here" from the visible intents (no extra clone), pending choices resolved by the rules' own `choose_card`, and potions counted from the legal `use_potion` actions (`run_state.player.potions` keeps a used potion until the fight ends, which made `search_v1`'s potion term inert).

**Measurement 1 (`search_v2`, 822 paired `val` combats from real `rules_v1` run states, `experiments/rl/results/combat-search_v2-n250-paired-eval.json.gz`).** Overall a tie (86.3 % vs 87.5 %, McNemar p = 0.34) with less HP lost (17.3 % vs 22.5 % of max HP, 95 % CI of the difference 3.8-6.6 points). Bosses 61.1 % vs 51.4 % (search-only 20, rules-only 6, p = 0.009). **Elites 75.6 % vs 91.5 % (search-only 7, rules-only 35, p = 1.5e-5), and 32 of those 35 lost pairs are one fight, the Phrog Parasite**: rules 96 % vs search 41 %, eight turns instead of six, 60 % of max HP lost instead of 25 %.

**Diagnosis (trace of the fight, `scratch` only).** A Phrog Parasite's death spawns four stunned Wrigglers (about 80 HP) that keep the fight going. The value function charged 0.55 per enemy HP point for every living enemy, so killing the parasite *raised* the enemy-HP sum and the planner left it at 1 HP and ended the turn, turn after turn, while its Infections and Lash took the player from 66 HP to 2. The policy had learned to exploit its own heuristic: a value function that rewards something other than winning is a defect to repair, not a result to report.

**Decision.** `search_v3` is `rules_v2` outside combat and `search_v2` inside it, with one change to the value: an enemy that was not there when the turn's search began (index at or above the root's enemy count; dead enemies stay in the list, spawns are appended) counts `spawn_weight` times as much (0.2). Search can be limited to bosses (`scope=boss`) or elites and bosses; the rules play the rest. Rule thresholds are exposed as a validated dictionary (`DEFAULT_TUNE`, defaults unchanged; replaying committed batches seed by seed is a regression test) and `slay2_sim tune` compares candidates paired on `dev`/`train` seeds only (it refuses `val` and `test`).

**Measurement 2 (`search_v3`, 780 paired `dev` combats, `experiments/rl/results/combat-search_v3-dev-paired-eval.json.gz`; development evidence, not held-out).** Overall win **87.8 % vs 83.5 %** (search-only 48, rules-only 14, p = 1.7e-5); HP lost 15.0 % vs 24.7 % of max HP (difference 9.7 points, 95 % CI 8.5-10.9). Bosses 50.0 % vs 38.0 % (24 vs 7, p = 0.0033), **elites 94.2 % vs 89.6 %** (10 vs 3, p = 0.092; the Phrog Parasite 95.7 % vs 100 %), monsters 96.9 % vs 94.8 % (14 vs 4, p = 0.031) with almost no HP lost (0.1 % vs 7.8 %). `spawn_weight=0` is indistinguishable (88.1 %); 0.2 stays because a spawn is not free in general. Potions are used more (1.10 vs 0.65 per combat). The sealed `test` partition is untouched.

**Measurement 3 (run level, `search_v3` against `rules_v2` on the same `dev` seeds; development evidence).** Searching **bosses only** (`scope=boss`, 499 paired games, `experiments/comparisons/search_v3-boss-vs-rules_v2-ironclad-a0-veteran-dev.json`): got past the Act-1 boss **71.9 % vs 64.1 %** (55 vs 16 discordant, exact McNemar p = 3.8e-6), mean floor **+0.78** (95 % bootstrap +0.29 to +1.27), 12 s per game against 0.7 s. A first run of **every fight** (`scope=all`, 198 paired games) gave 73.7 % vs 62.6 % (p = 0.006) and **+3.07 floors** (95 % bootstrap +1.76 to +4.39) at about 65 s per game, with one win. **Both runs, and every search batch before them, predate the isolation fix of ADR-035** (search on clones advanced the live game's card-id counter, which made the live game depend on how much the policy searched): they are valid simulated games but their action traces do not replay, and the single win of the all-fights run failed its replay audit, so that batch is not kept in the repository and its numbers stand only as a first look. The isolated re-runs replace them (see STATUS for what has been re-measured).

**What is not shown.** A better combat win rate is not a better run: it must carry through to the Act-1 and Act-2 bosses and to wins (the run-level paired batches on `dev`, then once on `val`, are the test; see Measurement 3 and STATUS). Search time per run is 12 s (bosses) to about 65 s (every fight) against 0.7 s for the rules.

**Alternatives rejected.** Hiding the elite failure behind the overall tie (the per-room table is the finding); special-casing the Phrog Parasite by id (the same flaw would reappear for the next spawner); a deeper rollout for every leaf (that is `search_v1`, and it was slower and worse).

**Rollback.** `search_v2` is unchanged and still registered; `search_v3` is additive.

## 2026-10-26 — ADR-035: deliberation must leave no trace in the game (an audit found that search steered the live run)

**Context.** The first win of a search policy (`search_v3`, every fight, seed 81161925) re-ran identically but failed the replay audit of ADR-032: "observation hash mismatch at step 486, phase COMBAT". The recorded action indices, applied to a fresh run, did not reproduce the run.

**Diagnosis.** At step 486 the live run's exhaust pile held two cards, the replay's one. Bisection with the rules policy and search-style play on clones between its decisions (clone, `fair_determinize`, step random legal actions on the copy): cloning alone, determinizing alone and stepping alone leave the live game untouched; determinizing and stepping together make it diverge (seed 81161925 at step 187, seed 3, seed 29; seeds 11, 17, 575912851, 1957840809 happened not to be affected within their horizon). The object graph of the live manager was byte-for-byte unchanged by the clone's play (a fingerprint of 3,299 reachable values); of 3,284 module-level and class-level values in the simulator exactly one changed: `sts2_env.cards.base._next_instance_id` (3 to 19), the global counter that numbers every card instance. A card a clone creates (an Infection, a Wound, a copy) therefore advances the counter the live game uses next, and something in the simulator depends on the absolute value of those ids (the way a set of integers iterates is the likely route; not pinned down further). Consequences: the live game's evolution was a function of how much the policy searched (not of the seed and the actions alone), the action traces of search policies do not replay, and in principle a policy could steer hidden randomness by burning ids. The harness never read a hidden value (the fairness tests stand); this is the opposite problem, the policy changing the world it is meant to only observe.

**Decision.** `slay2_sim/isolation.py::deliberation()` snapshots the counter before a policy decides and restores it afterwards, in a `finally`; the runner wraps every `policy.act` in it, as does the combat evaluator. Clones are discarded by then, so re-using their ids is harmless. New manifests say `deliberation_isolated: true`; the site exporter marks a search batch without it as "before isolation" and `/methods` shows that. A search batch whose win cannot be replayed is not published (ADR-032 already refuses it), and its numbers are re-measured on isolated runs instead of being carried forward.

**Evidence.** `sim/tests/test_isolation.py`: on seed 81161925 clone play without the guard changes the live trajectory (the test proves its own power), with the guard it is identical observation hash for observation hash over 260 decisions; the counter is restored exactly, also when the policy raises. A wider check (seeds 3, 11, 17, 29, 575912851, 1957840809, up to 900 decisions): identical with the guard on all six, different without it on two. The rules policy's committed batches are unaffected (it does not clone).

**What was not re-measured.** `search_v1` (obsolete; its batch is flagged), the `search_v2` combat evaluation on `val` (a negative finding about a defective value function, still true), and the `search_v3` development combat evaluation: these are simulated combats that are valid as played, and the run-level evidence (the claims that matter) is what is re-run. Everything is labelled with what it was produced by.

**Rollback.** Remove the wrapper in `runner.py` / `evalcombat.py`; nothing else depends on it, but search traces will again fail the replay audit.

## 2026-10-26 — ADR-036: the pilot's hand-written thresholds are tuned on development seeds only, and the result is tested once on held-out seeds

**Context.** `rules_v2` plays everything outside the card reward with thresholds written by hand before any evidence existed (`DEFAULT_TUNE` in `policies/rules.py`: when to fight an elite, how much HP triggers a rest, when a shop is worth entering, how big a deck may grow, when a potion is drunk, and so on). The measured card values improved the card picks by 22 percentage points (ADR-031); the other thresholds were never examined. Changing them is cheap, which is exactly why the procedure has to be fixed first: with 25 numbers and 2,000 games a search will find "improvements" that are noise.

**Decision.** Ironclad, A0, `veteran` profile, base policy `rules_v2` with `experiments/cardvalue/ironclad-a0-v1.json` (sha256 `8b3fe2f4d88b87dc…`) and `threshold` 0, the policy that ADR-031 validated. Nothing is tuned on `val` or `test`: `slay2_sim tune` refuses those partitions in code. The card-pick rule, the values and the search settings are not touched. Four stages, each on seeds no earlier stage used:

1. *Screen* (`dev[1000:1500]`, 500 paired games per candidate). One threshold changed at a time, from the grid below, against the unchanged base. A candidate advances if the share of games that got past the Act-1 boss is higher than the base's with an exact two-sided McNemar p < 0.10, at most the best eight by paired mean floor. (This stage is meant to be generous; it is not evidence.)
2. *Confirm* (`dev[2000:3000]`, 1,000 paired games). Each advanced candidate against the base; it is confirmed if it is higher on the same endpoint at level 0.05 / (number advanced). Of several confirmed values of one threshold the one with the larger mean-floor gain is kept.
3. *Combine* (`dev[3000:4000]`, 1,000 paired games). The base with every confirmed change at once against the base; it must be higher on the endpoint at level 0.05, otherwise the combination is dropped and nothing is adopted.
4. *Test* (held-out `val`, once). The combined policy on the 2,000 `val` seeds against the existing `rules_v2` `val` batch (`rules_v2-ironclad-a0-veteran-val-n2000`; same seeds, paired). Primary endpoint: got past the Act-1 boss, exact McNemar, level 0.05. Secondary, reported: mean floor with a paired bootstrap interval, got past the Act-2 boss, wins (each re-derived by `audit wins`). Passing means the thresholds are adopted as `rules_v3` (additive; `rules_v2` stays); failing means they are not, and the result is published either way.

**Grid (stage 1; 39 candidates and the base).** `elite_ok_hp` 0.6 / 0.7 / 0.9; `elite_value` 0.5 / 1 / 3 / 4; `elite_ok_floor` 0 / 2 / 8; `elite_mid_value` −1 / 1; `heal_below` 0.5 / 0.6 / 0.8; `boss_heal_below` 0.7 / 1.0; `rest_weight` 1.5 / 5; `shop_rich` 0 / 2.5; `treasure_value` 1 / 3; `unknown_value` 0.2 / 1.5; `shop_card_threshold` 2.8 / 4.4; `shop_potion_margin` 0 / 100; `potion_hp_frac` 0.08 / 0.3; `danger_frac` 0.2 / 0.45; `max_deck` 26 / 40; `monster_hp_penalty` 0 / 1.5; and the card-pick `threshold` 0.1 / 0.2 (the validated 0.0 is the base). The defaults sit between the grid points on purpose.

**Why this and not an optimiser.** A joint search (CMA-ES, Bayesian optimisation) over all the thresholds on development seeds fits the development seeds; one change at a time, a fresh-seed confirmation with a multiplicity correction, a combined check on more fresh seeds and one held-out test is slower to a result but every step can be audited and repeated. Wins are too rare to be an endpoint (0.30 % on `val` for `rules_v2`); "got past the Act-1 boss" is the endpoint ADR-031 already used and the one the site reports.

**What this does not claim.** Nothing about the live game; nothing about other classes (the thresholds are tuned for one pilot on Ironclad at A0); nothing about winning (the policy wins about 1 game in 300 in simulation, and a few percentage points at the first boss does not change that order of magnitude). If a threshold helps only in the way the simulator is wrong, the tuning would not show it.

**Alternatives rejected.** Tuning against the 500 `dev` games already used for the search comparisons (those results would then depend on the tuned policy); picking the best of the screen without confirmation; using `val` for stage 3 (it would stop being held out).

**Rollback.** Nothing is adopted until stage 4 passes; `rules_v2` is not modified, tuned values live in a separate policy name.

## 2026-10-26 — ADR-037: a game must not depend on how many games its process played before it (the sample audit found the simulator does)

**Context.** The new `audit sample` (red-team campaign 6) re-runs a random sample of completed games of a held-out batch and replays each trace observation hash by observation hash. In the first pass, 4 of the 160 games sampled from the Ironclad, Regent, Necrobinder and Defect `rules_v2` batches (one per batch) did not replay: replaying the recorded actions in the same process diverged at a combat step (at step 251 to 441); in three of them the fresh re-run still reproduced the stored record, in the Regent one its step count differed too. The Silent `rules_v2` sample (40 games), the `rules_v1` samples (200) and `random_legal` (40) were clean.

**Diagnosis.** Seed 1725454781 (Ironclad): at step 441 the discard pile held one Anger in the policy run and two in the replay; the action taken at step 440 (play Anger) was identical in both. Replaying the recorded actions in a *fresh* process matched all 459 steps; replaying them after any earlier game of the same process diverged at step 441, whatever the starting value of the global card-id counter (`new_run` resets it). So the first game of a process differs from every later one. The card-id counter first differs at step 33, a `choose` of the reference-only card Vicious: the call stack is `upgrade_card -> capture_self_mutating_card_progress -> _reference_card_base_values` (an unbounded `lru_cache` in `sts2_env/cards/base.py`) `-> create_card -> make_vicious -> _get_next_id`. The first call per (card, upgraded) in a process builds a card to read its base values and keeps the instance id it took; its sibling `_probe_factory` restores the counter, this path does not. After that miss every id of the game is one higher than in any later game of the process, and in rare situations a pile differs (Anger's added copy). The final outcome of the example was identical in both states (459 steps, same floor, HP and killer): the difference is real but usually does not propagate.

**Decision.** The harness puts every process in the state all but its first games already have: `slay2_sim/warmup.py::warm_simulator()` calls the simulator's lazy card lookups once for every card (`card_metadata`, `card_preview`, `is_basic_strike_or_defend_card_id`, and `_reference_card_base_values` for both upgrade states) before the first game, outside any game, and restores the counter (`new_run` resets it anyway). It runs at the first `new_run` of a process. The third-party checkout is not modified. A check of every `lru_cache` in `sts2_env` over 30 games of all five classes after the warm-up found none that still grew. New manifests say `canonical_process_state: true`. Gap G10 records the simulator defect; `SLAY2_NO_WARMUP=1` switches the warm-up off for the test.

**Evidence.** `sim/tests/test_process_state_determinism.py` plays seed 1725454781 in a fresh subprocess and replays it in the same process as that process's second game: with the warm-up all 459 hashes match, with it switched off the replay diverges at step 441 (the test proves its own power). After the fix the same 11 held-out batches were sampled again (40 games each, 440 in all): every game was re-derived, replayed hash for hash and ended in the claimed terminal state. `slay2_sim audit rederive` re-runs *every* game of a batch in fresh workers and compares outcome, floor, act, HP, deck size, relics, combats won, steps and killer with the stored record; its result for the five `rules_v2` held-out batches is below.

**Result of the complete re-derivation (the five `rules_v2` held-out batches, 10,000 games, after the fix).** **9,994 of 10,000 games were re-derived exactly** (Ironclad 2,000 of 2,000, Regent 2,000 of 2,000, Defect 1,999, Silent 1,998, Necrobinder 1,997). The six that differ are exactly the kind of game the defect touches, and none of them changed its outcome or the act it ended in (so the primary endpoint and every win are unaffected): five differ in the step count only (Silent seeds 1481468527 and 1821855013 by one step; Necrobinder 1303472829, 1507301659 and 2012744721 by 10, 9 and 1 steps), and one Defect game (seed 417516746) died two floors later than stored (floor 31 against 29, killed by The Insatiable instead of a Chomper). The records stay as they were produced; `rederivation-audit.json` in each batch lists the differing seeds with both values, and `/methods` shows the count.

**What this does and does not change.** Every batch before this commit was produced without the warm-up, so the first games of each worker ran in the other state (the games that first met a reference-only card, a handful per worker). The simulated games are still valid games of this simulator and the comparisons are paired on seeds, so a rare, process-dependent perturbation of this size cannot move them; the complete re-derivation counts exactly how many stored games it touches. What it does break is the claim "this seed and this policy always give this game", which now holds by construction for new runs and by audit for old ones. It says nothing about the live game (gap G5).

**Alternatives rejected.** Restoring the counter around every call into the simulator (it would need patching the third-party code or wrapping dozens of call sites); running each audited game in its own process (the stored records were produced by warm workers, so a fresh-process re-run would disagree with them for exactly the games the defect touches); leaving the sample audit's failures as "known" (a replay audit that is allowed to fail is not one).

**Rollback.** Remove the call in `runner.new_run`; replay audits will again fail for the rare games that depend on the process state.


## 2026-10-26 — ADR-038: Route Lab compares what routes pay, exactly, and never whether you survive them

**Context.** Phases 05 and 06 ask for a Map Pathfinder. The first thing the verified rules support is not a node-and-edge map editor but the question a player asks at every fork: what do the rooms on each path pay? The map rules are now read from the game's source (MAP-1 to MAP-6, REST-1, ANC-1 and TRS-1 in `docs/game/MECHANICS-COVERAGE.md`, section 11), and the hidden state that rooms move (the "?" counters, the rare-card counter, the potion chance) is already modelled exactly. Nothing validated says which route is *safer*: that needs hit points, a deck and fight outcomes, and the only run-level evidence is from a simulator that has not been compared with the live game.

**Decision.** `/routes` (Route Lab) and `POST /api/v1/odds {calculator:"route"}`: up to three routes of at most 20 rooms (monster, elite, "?", rest, shop, treasure; at most 12 "?"), typed as letters or built with buttons, kept in the page link. For each route the engine (`packages/odds/src/route.ts`) returns, exactly and as fractions: the room counts; the distribution of what the route's "?" rooms turn into, from the "?" counters seen so far this act; the chance that a rare card is offered at least once and the expected number of rare cards (one pack of three cards per fight against the rare-card counter, elites at elite rates); the chance of at least one potion and the expected number of potions (one roll per fight against the stored potion chance); the expected gold of fights and treasure rooms with its range; expected relics (elites plus treasure rooms). The starting counters are explicit inputs and are printed on the page (never silently "the start of a run"); a saved run can supply them from its logs, which stay in the browser. Treasure gold (TRS-1: 42 to 52, A3 takes 75 % of the value drawn) is a new exact rule with its own oracle cases.

**What it does not do.** No win probability, no "best route", no hit-point model, no ranking or highlighting of rows: the page says "Rooms, not survival". Relics that change packs or "?" rooms, shop stock, event contents, boss rooms and the first-run script are listed as not modelled in the `route` provenance entry.

**Method.** The "?" counters move only at "?" rooms; the rare-card counter and the potion chance move only at fights; a "?" is a fight with the probability its counters give. The walk carries the joint distribution of (unknown counters, one side counter, "has it happened yet") as integers over one common denominator (every per-step probability is a whole number of 1/100, 1/1,000 or 1/10,000, which the code asserts), once for the rare-card counter and once for the potion chance, and divides once at the end. On the test machine (shared, load about 7 on 4 cores) a route of 17 rooms with six "?" takes about 50 ms and the longest route the schema allows (12 "?" and eight monsters) about one second; the API bounds a request at 20 "?" rooms across its routes (two routes of ten take about a second; RT-10-14) and charges route requests by their cost (one unit per route and per "?" room, 60 units a minute per client), while the page evaluates any route in the browser.

**Evidence (three layers, as for the other engines).** (1) 16 cases from the independent Python oracle (`oracle_odds.py route_report`: one forward pass over the whole joint state, a different structure) are reproduced exactly, including A3 and A7, a long run of events, vague histories and the treasure-gold rule (golden file 739 cases, 16 kinds, the earlier 720 unchanged). (2) Brute-force enumeration of every world (every card, every potion roll, every "?" outcome) for 8 routes × 2 rule sets × 4 counters, 4 routes × 5 potion chances, the "?" outcome distribution for 0 to 6 rooms and a recorded-history case. (3) Agreement with the other engines and the published figures: six "?" rooms hold 1.3902 fights in expectation (the sum of the published marginals), an elite pack right after a rare holds a rare 16.95 % of the time and a regular pack never, fights alone reproduce `forecastPotions`, one fight reproduces `forecastPack`; fast-check properties (probabilities in [0,1], the four "?" outcomes share the "?" rooms, rest and shop rooms change nothing else, one more fight never lowers a chance of getting something). The page and the API call the same engine; 11 browser tests on each of two viewports (axe WCAG 2.2 AA, no horizontal overflow), 12 API tests, and the red-team beta-refusal list cover them.

**Alternatives rejected.** A node-and-edge map editor first (a whole map has dozens of nodes and edges to enter by hand; the evaluation core is the same and an editor can feed it later); ranking routes by an invented score (nothing validated supports one); including the boss (its pack is three rares and would distort every "at least one rare" figure, and it is the same on every route); Monte Carlo (the state space is small enough to be exact).

**Rollback.** Remove `/routes`, the `route` calculator and `route.ts`; the oracle cases stay valid and unused.

2. *Advisor.* The page is drawn on the server in its "no saved run" state (the layout a first visit has). Every control is disabled until the page is interactive, so a click can never land before its handler exists. A visitor with a saved run still sees it replace that state after hydration (user data, not a loading placeholder).
3. *Pinned by a test.* `apps/web/e2e/stability.spec.ts` (desktop and phone): the cumulative shift of each of the seven pages is below 0.02, the landing page and the advisor also on the slow-4G profile (150 ms round trip, 1.6 Mbit/s), and the server-drawn advisor with scripts blocked has its controls disabled.

**Measured.** After: 0 (to four decimals) on all seven pages, both viewports, fast network and slow-4G. The new tests fail on the previous build (9 of 20: 0.093 and 0.091 on a desktop, 0.297, 0.122 and 0.313 on a phone) and pass on this one (20 of 20). The display font was used on 6 of 6 cold loads at 20 ms / 50 Mbit/s, 60 ms / 9 Mbit/s and 100 ms / 4 Mbit/s, and on 0 of 6 at the slow-4G profile, where the page shows the fallback on its first load. The existing 40 advisor, journey and landing browser tests pass unchanged.

**Not measured.** Lighthouse was not run (the tool would have downloaded and executed an external package, which was refused); the other Web Vitals were measured in the lab with `pnpm --filter @slay2/web vitals` (`docs/DEPLOY.md`, "Web Vitals (lab)": largest contentful paint 0.26 to 0.42 s on a desktop and 0.96 to 1.75 s on a throttled phone; INP needs a person). The shift is a lab measurement on a shared development machine against `next start` on localhost with emulated network conditions, not field data. The same pass found that the 700 weight of the display font was fetched on every page and used on none (15 KB), and dropped it. `local()` fallbacks name Times New Roman and Arial, which exist on Windows, macOS and iOS but not in the Linux container used here (the container's fallback is its own serif and sans, unadjusted); the zero holds there anyway because `optional` never swaps.

**Alternatives rejected.** `swap` with only the metric-matched fallback (above); inlining the font as a data URI (30 to 120 KB on the critical CSS path, and `font-src` would need `data:`); fixed heights for the headings (breaks at every width); keeping the skeleton and tuning its heights (the right heights depend on the visitor's saved run, which the server cannot know).

**Rollback.** Revert the commit: the previous fonts came from `@fontsource` CSS imports and the advisor's gate from `useHydrated`, both in git.

## 2026-10-26 — ADR-043: every page fits the phones, tablets and small laptops people have (320 to 1280 px), and a test sweeps those widths

**Context.** The suite's phone project is a Pixel 7 (412 px), which is exactly the width at which the header's six links still fit (they need 400 px), and its desktop project is 1440 px. Probing every page with the browser at 320, 340, 360, 375, 390, 412, 640, 700, 768, 800, 900, 1024 and 1280 px (document width against viewport; every element whose box leaves the screen outside a scroll container; text that an `overflow: hidden` box cuts off) found six defects that no test could see: (1) the header navigation was one row of six links, so every page scrolled sideways by 10 px at 390 px (an iPhone), 25 px at 375, 40 px at 360 and 80 px at 320, and "About" (at 320 also "Methods") was cut off; (2) on `/methods` an implicit grid column took the width of its widest unbreakable run (a file path such as `experiments/cardvalue/silent-a0-v1.json` in the paired-comparison list), 16 px past a 375 px phone and 71 px past a 320 px one; (3) the long "Parity with the live game unverified" chip could not wrap (`whitespace-nowrap`), 43 px past a 320 px phone; (4) the advisor's compact character cards (shown once a class is chosen) clipped "Necrobinder" and the word "selected" at every width from 320 to 1024 px (two columns up to 640 px, five columns from there); (5) at 768 px the build badge appeared in a row that did not have the room, 10 px past an iPad's width; (6) for a visitor with a saved run the "Resume · Ironclad A0" chip made the header 40 to 120 px wider than a screen of 640 to 800 px.

**Decision.**
1. *Header.* Below `md` (768 px) the six links are a three-column, two-row grid (each target at least 44 px tall and a third of the width) and the header is not sticky; from `md` up the row is as before, with the build badge from `lg` and the resume chip's class and ascension from `xl` (below that it reads "Resume"; below `md` it is not shown, the links are the way back).
2. *Grids.* A base-layer rule gives every `.grid` a `minmax(0, 1fr)` column, so the implicit column can shrink to its container; the `grid-cols-*` utilities, which come later, still decide the columns wherever a grid sets them (checked on the responsive grids of `/methods`, `/codex` and `/odds`). `overflow-wrap: break-word` on `body` lets a path or an id longer than its box break instead of widening the page (not `anywhere`, which would also shrink table columns).
3. *Badge.* It wraps on phones and stays on one line from `sm` up.
4. *Character picker.* Once a class is chosen the five cards become chips that flow with their names (a check mark for the selected one) below `lg`, and cards again from `lg` up, with the word "selected" from `xl` and a check mark between.
5. *Pinned.* `apps/web/e2e/phone-widths.spec.ts` (the mobile project; the page, the box and the text checks are `expectNoHorizontalOverflow`, the document width and the new `expectNoClippedText`): at 320 / 360 / 390 px eleven page states (every page, the five odds calculators, the route lab with three routes), the advisor with an offer, and "every header link is on the screen and at least 44 px tall"; at 640 / 768 / 1024 / 1280 px the advisor with an offer, the route lab, the codex, the rewards calculator and the header of a visitor with a saved run (the chip is visible from 768 px and not below). 59 tests; the 39 phone cases fail on the previous header, grid rule and badge, and the tablet cases failed on the previous header, chip and picker before each was fixed.

**Measured.** After the change the probes find no overflow and no cut-off text at any of the thirteen widths on any of the seven pages and the advisor with an offer and with a saved run. The existing browser suite is unchanged.

**Not covered.** Landscape phones other than by width (the sweep is by width, not orientation), browser zoom and text enlargement beyond 200 %, and iOS Safari itself (Chromium's emulation does not reproduce its address-bar and safe-area behaviour).

**Alternatives rejected.** A hamburger menu (it hides the six destinations behind a tap and needs a client component with focus management for no gain at six links); a horizontally scrolling nav row (the cut-off link is what was wrong); shrinking the nav text (still 310 px of text and padding at 320 px, and smaller than the 14 px body); truncating the class names with an ellipsis (a name is the thing being chosen).

**Rollback.** Revert the commit; no data or API is touched.
